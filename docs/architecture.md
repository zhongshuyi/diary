# 应用架构与目录边界

## 目标

此刻是一个本地优先的多端日记应用。用户应当可以在手机上随时留下短记录，也可以在 Windows 上用键盘和宽屏整理、检索和回看。两种场景的操作习惯不同，因此客户端是两个独立应用，而不是同一套页面做响应式缩放。

## 客户端边界

| 客户端 | 技术 | 首屏任务 | 交互重点 |
| --- | --- | --- | --- |
| Mobile | Flutter | 立即写下一个瞬间 | 底部导航、单手点击、快速捕捉、离线优先 |
| Desktop | Electron + React | 扫描时间线并持续编辑 | 自绘标题栏、键盘快捷键、多栏布局、工作区导航 |

两端禁止直接复用 UI 页面。可以复用的只有协议字段、业务语义和测试样例；平台交互由各自的 shell 负责。

## 数据流

```text
用户输入
  ↓
客户端本地存储（立即可见）
  ↓ 产生 mutationId
本地 outbox
  ↓ 网络可用时批量 POST
server /api/v1/sync
  ↓ 游标增量拉取 + 冲突结果
客户端合并并清理已确认 mutation
```

本地写入永远不等待网络。同步失败只影响同步状态，不阻塞写日记。

实现约定：桌面端的本地存储由 Electron main 进程持有 SQLite 连接，renderer 只能通过 preload 暴露的业务 IPC 访问。renderer 的 `localStorage` 只在首次启动时作为 v1 迁移输入，迁移前会写入用户数据目录的恢复副本；正式记录、草稿、outbox、游标和设置不再以 `localStorage` 作为主存储。

桌面本地 schema 可以先于跨端 wire schema 演进。当前本地记录通过兼容映射发送协议 v1；当移动端开始接入 v2 时，再切换到可空 `mood`、独立 `occurredAt` 和附件实体。

## 同步决策

- 记录以 `id` 作为跨端稳定主键。
- 每次修改生成客户端唯一的 `mutationId`，服务端按 mutation 幂等处理。
- 当前版本使用确定性的 last-write-wins：先比较 `updatedAt`，相同时比较 `deviceId`，再相同时比较 `mutationId`。
- 删除使用软删除（`isInTrash`），服务端保留变更记录，避免另一台设备把删除内容重新拉回。
- 桌面端导入的图片和视频先复制到 Electron 应用数据目录，日记本地记录保存应用内路径；同步协议当前只同步附件清单/路径，二进制上传单独演进，不把大文件塞进同步 JSON。
- 服务端当前使用 JSON 文件存储作为可运行的开发实现，存储接口与协议解耦，后续可替换为 SQLite 或 PostgreSQL。

## 迁移与回退

这次目录迁移只改变 Git 内的路径，不删除任何原有 Flutter 文件。回退时可以将 `mobile/` 内容移回仓库根目录；旧版本提交仍完整可用。桌面端和服务端是新增目录，未修改移动端的数据模型，降低混合版本运行风险。

发布同步协议时先采用 `schemaVersion: 1` 和 `protocolVersion: 1`。新增字段必须向后兼容；删除或改变字段语义时新增协议版本，不在客户端静默破坏旧数据。
