# 桌面端产品完善与实施方案

> 状态：已确认，作为桌面端后续实现和验收基线
> 更新日期：2026-09-16
> 适用范围：`desktop/`、与桌面能力直接相关的 `server/` 协议演进，以及未来 `mobile/` 的能力对齐
> 产品约束：先完善桌面端以快速验证功能，不把桌面端定义为唯一主产品；最终桌面端与 APP 同等重要

## 当前实现进度（2026-09-16）

当前已完成 Phase 0–1 的数据底座、Phase 2 的系统级速记主链路，并持续推进 Phase 3–5 的桌面管理切片：

- 已加入 desktop Node test 入口，覆盖 schema 初始化、事务回滚、v1 导入、草稿、同步合并、回收站和中文搜索。
- 已验证目标 Node 运行时的 `node:sqlite` 与 SQLite FTS5 trigram 能力；10,000 条基准数据最近一次首屏列表为 4.15 ms，中文搜索为 8.15 ms（基准脚本：`desktop/scripts/benchmark-database.cjs`）。
- 已把桌面日记主存储迁移到 Electron main 进程 SQLite，localStorage 仅作为首次迁移输入和恢复来源。
- 已实现 localStorage v1 JSON 恢复副本、一次性迁移、记录/草稿/outbox/settings 的 IPC 边界，以及同步结果回写。
- 已接入 500 ms 草稿自动保存和启动恢复；正式保存、回收站、恢复和 outbox 使用事务。
- 已接入独立速记 BrowserWindow、`Ctrl+Shift+Space` 全局快捷键、托盘入口、后台驻留和真正退出菜单。
- 速记窗口支持复用现有文字/媒体粘贴与拖入编辑器，独立保存 `quick-capture` 草稿；保存后隐藏并恢复此前窗口焦点。
- 已补充快捷键解析、速记草稿按 ID 恢复测试，并通过 Electron 启动冒烟验证（GPU 驱动警告不影响窗口启动）。
- 设置页可修改速记快捷键；新快捷键注册失败时会重新注册旧快捷键并显示冲突原因。速记窗口坐标写入 settings，并在多屏切换后避免恢复到完全离屏位置。
- 已开始 Phase 3–5 的真实记录管理：新增“全部记录”、分页加载、回收站恢复/永久删除、收藏、复制、移入回收站、键盘打开记录和分类/标签统计筛选；列表已支持批量收藏/移入回收站与撤销。搜索使用 SQLite FTS/短词 LIKE 并支持组合筛选。附件已开始登记稳定实体、SHA-256、受管相对路径和引用关系，包含一次性迁移回填；设置页展示可用/缺失/待清理数量；媒体库支持筛选、按需图片缩略图和返回所属记录，查看器可对缺失附件重新定位并校验哈希。已实现版本化 `.diary.zip` 备份导出、导入前预览和按稳定 ID 合并恢复；导入先写入唯一 staging 目录，数据库失败会删除本次新文件并返回失败阶段/清理数量，启动时按宽限期清理崩溃遗留的 staging 和孤儿附件；bootstrap 后生成每日滚动备份。分类/标签页支持平铺一键筛选、就地重命名、删除和重命名到已有标签时的自动合并。永久删除会事务清理本地记录、搜索索引和未同步 mutation，有集成测试。跨端墓碑将在同步 v2 处理。

仍待后续阶段实现：真实缩放/多屏 E2E 和完整速记 E2E（Phase 2 后续）、附件引用级撤销（Phase 3/5 后续）、独立分类/标签关系表（Phase 4 后续）、附件批量修复、Markdown/PDF 导出和跨端附件同步（Phase 5–7）。本轮没有把这些功能伪装成已完成。

## 1. 已确认的产品决策

1. 工作和个人记录存放在同一个资料库中，不拆分为多个工作区。
2. 每条记录最多属于一个分类，可以拥有多个标签。
3. 从网页复制内容时，只保存用户主动粘贴的文字或图片；不自动保存来源 URL、网页标题、浏览记录等信息。
4. 桌面端首先完成数据安全、速记、管理和检索闭环，再将验证后的能力迁移到 APP。
5. 产品保持日记属性，不扩展为任务、项目或知识库管理工具。
6. 核心体验排序为：**可靠保存 > 快速记录 > 容易找回 > 长期回顾 > 跨端同步**。

## 2. 当前状态与主要问题

### 2.1 已有基础

- Electron + React 桌面壳层、自绘标题栏、浅色/深色主题。
- 今日记录、日历、媒体、洞察和设置等页面骨架。
- 支持一天多条记录、可选标题、分类、心情和图片/视频/音频附件。
- 支持粘贴剪贴板文字与媒体、拖入媒体文件，并把媒体复制到应用数据目录。
- 已有本地优先同步协议、outbox、游标和服务端幂等 mutation 的初步实现。
- Flutter 端已有较完整的记录数据模型、回收站、媒体、洞察、备份等页面基础。

### 2.2 必须先解决的问题

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 桌面记录存放在 `localStorage` | 数据量、事务、迁移、查询和故障恢复能力不足 |
| P0 | 编辑中的内容没有真正自动保存 | Esc、点击遮罩、窗口关闭或崩溃可能丢失输入 |
| P0 | 没有系统级速记入口 | 用户必须先找到并打开主窗口，打断当前工作 |
| P0 | 记录生命周期不完整 | 缺少收藏、删除、恢复、永久删除、复制和批量操作 |
| P0 | 搜索入口与页面行为不一致 | 用户无法形成稳定的查找心智模型 |
| P0 | 标签和回收站仍是占位页 | 组织与误删恢复无法闭环 |
| P1 | 媒体只记录本机绝对路径 | 备份、迁移和跨端同步后容易失效 |
| P1 | 冲突直接使用服务端版本 | 用户的另一份内容可能无提示地不可见 |
| P1 | 字号偏小、层级重复、空白过多 | 长时间阅读费力，宽屏空间利用不合理 |
| P1 | 部分卡片与图标不可键盘操作 | 不符合桌面操作习惯和无障碍要求 |
| P1 | 桌面端没有自动化测试入口 | 数据迁移和核心流程修改缺少回归保护 |

## 3. 产品目标和衡量标准

### 3.1 桌面阶段目标

- 用户在其他软件中按一次全局快捷键即可开始输入或粘贴截图。
- 任意时刻关闭速记窗口、主窗口或应用崩溃，最近草稿都能恢复。
- 用户可以从“全部记录”进入任何历史内容，不依赖逐月翻日历。
- 用户可以按文字、分类、标签、日期、心情、收藏和附件类型组合查找。
- 用户可以导出一份包含正文和媒体的完整备份，并在另一台电脑预览后恢复。
- 所有核心状态都说明清楚：已保存、待同步、同步失败、存在冲突、正在恢复。

### 3.2 可验收指标

| 指标 | 目标 |
| --- | --- |
| 已运行应用的速记窗口唤起时间 | P95 小于 300 ms |
| 普通文字输入后的草稿落盘延迟 | 停止输入 500 ms 内 |
| 本地保存反馈 | 100 ms 内出现“已保存到本机”状态 |
| 10,000 条纯文本记录的普通搜索 | P95 小于 150 ms |
| 10,000 条记录的首屏时间线读取 | P95 小于 200 ms，分页加载 |
| 数据迁移 | 记录数量和附件引用 100% 对账，无静默跳过 |
| 键盘可达性 | 新建、编辑、保存、搜索、筛选、删除、恢复可全键盘完成 |
| 关键流程自动化覆盖 | 数据仓库、迁移、草稿、搜索和删除恢复均有测试 |

这些指标在开发机上以固定测试数据集测量。性能目标不以牺牲数据可靠性为代价。

## 4. 核心使用场景

### 场景 A：工作中记录一句话

用户正在浏览网页或聊天，复制一段文字，按 `Ctrl+Shift+Space` 打开速记，粘贴后按 `Ctrl+Enter` 保存。窗口自动隐藏，焦点返回原应用。产品不采集来源页面。

### 场景 B：保存系统截图和当时心情

用户用 Windows 截图工具把截图放入剪贴板，打开速记窗口并粘贴图片，补充一句说明。心情和分类可以当场填写，也可以稍后整理。

### 场景 C：持续记录工作片段

用户在主窗口的“今天”中持续写多条短记录。每条记录独立保存并带准确时间，不要求标题。用户可给工作项目添加标签，但产品不把标签变成项目管理系统。

### 场景 D：找回过去内容

用户按 `Ctrl+K` 搜索关键词，进一步筛选“工作”“有图片”“收藏”“最近三个月”，直接打开结果并看到命中高亮和上下文。

### 场景 E：回顾与整理

用户在周末查看本周回顾，补充标签、收藏重要片段，或把误删内容从回收站恢复。回顾提供线索，不用连续打卡制造压力。

### 场景 F：备份和换设备

用户导出备份包。导入时先看到记录数、附件数、时间范围和冲突处理方式，确认后合并，不默认覆盖现有资料库。

## 5. 范围与优先级

### 5.1 P0：桌面可用闭环

- SQLite 本地数据库和可恢复的数据迁移。
- 自动草稿、崩溃恢复和窗口关闭保护。
- 系统级快捷键、独立速记窗口和托盘行为。
- 今天、全部记录、详情/编辑、收藏、复制、删除、回收站和恢复。
- 全局搜索与基础筛选。
- 分类和标签的真实持久化管理。
- 剪贴板图片、拖入附件和媒体文件生命周期。
- 基础备份与恢复。
- 核心自动化测试与可观察错误状态。

### 5.2 P1：长期使用价值

- 模板：普通日记、一句话、心情、工作日志、会议记录、周回顾。
- 记录版本历史和手动恢复。
- 高级筛选、保存的筛选条件和批量整理。
- 本周/本月回顾、往年今日、收藏回顾和情绪趋势。
- PDF、Markdown 和完整 ZIP 导出。
- 可选应用锁、空闲自动锁定和隐私模式。
- 附件上传、下载、校验与跨端同步。

### 5.3 暂不实施

- AI 自动写作、总结、情绪推断或内容分类。
- 网页来源 URL、网页标题和浏览上下文自动采集。
- 持续监听或保存剪贴板历史。
- 多人协作、公开分享、社交动态和评论。
- 任务清单、看板、项目排期和提醒中心。
- 地图、天气和自动位置记录。
- 多资料库、多层文件夹或块编辑器。
- 为指标而设计的连续打卡和游戏化奖励。

## 6. 信息架构

### 6.1 一级导航

| 入口 | 主要任务 | 默认内容 |
| --- | --- | --- |
| 今天 | 快速记录并查看当日片段 | 当日时间线 + 常驻编辑区 |
| 全部记录 | 浏览、筛选和批量管理 | 按发生时间倒序的分页列表 |
| 日历 | 按日期定位记录 | 月历 + 当日记录列表 |
| 媒体 | 浏览所有附件 | 图片、视频、音频，可回到原记录 |
| 回顾 | 重新发现和理解内容 | 本周、本月、往年今日、收藏 |
| 标签 | 查看和管理主题 | 标签列表、使用次数、关联记录 |
| 回收站 | 恢复或永久删除 | 按删除时间排序的记录 |
| 设置 | 控制应用行为 | 速记、数据、同步、外观、隐私、快捷键 |

### 6.2 全局入口

- `Ctrl+Shift+Space`：在系统范围打开/隐藏速记窗口，可在设置中修改。
- `Ctrl+N`：在当前主窗口新建完整记录。
- `Ctrl+K`：打开全局搜索/命令面板。
- `Ctrl+Enter`：保存当前记录。
- `Ctrl+,`：打开设置。
- `Esc`：关闭当前浮层或隐藏速记窗口；有草稿时先自动落盘，不丢弃内容。

快捷键冲突时必须显示原因和修改入口，不能悄悄失效。

### 7.1 速记与编辑

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| CAP-01 | P0 | 注册可配置的系统级速记快捷键 | 应用在后台运行时可唤起；注册失败时设置页明确提示 |
| CAP-02 | P0 | 使用独立轻量速记窗口 | 自动聚焦正文，不显示主导航，窗口位置记忆并限制在可见屏幕内 |
| CAP-03 | P0 | 支持纯文本粘贴 | 只保存用户粘贴的文字，不附加 URL 或网页元数据 |
| CAP-04 | P0 | 支持剪贴板图片和文件粘贴 | 先复制到受管理附件目录，再建立数据库记录 |

| CAP-07 | P0 | 快速模式保持最少控件 | 默认只显示正文、附件、保存；分类/标签/心情在“更多”中按需展开 |
| CAP-08 | P0 | 可展开到完整编辑器 | 展开后保留全部草稿、附件、日期和焦点上下文 |

| CAP-10 | P1 | 提供少量模板 | 模板只预填结构，不改变记录数据模型，可随时切换为普通记录 |

### 7.2 草稿与数据安全

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| SAFE-01 | P0 | 输入停止后自动保存草稿 | 500 ms 内事务落盘，界面展示“保存中/已保存/保存失败” |
| SAFE-02 | P0 | 草稿与正式记录分离 | 未提交草稿不进入时间线，不参与同步，不计入统计 |
| SAFE-03 | P0 | 崩溃或重启后恢复草稿 | 重启后恢复正文、附件、日期、分类、标签和心情 |
| SAFE-04 | P0 | 关闭行为不丢内容 | Esc、遮罩点击、关闭窗口、系统注销前均先提交草稿事务 |
| SAFE-05 | P0 | 保存正式记录具备原子性 | 正文、标签关系、附件关系和 outbox mutation 在同一事务提交 |
| SAFE-06 | P1 | 保存有限版本历史 | 每次显式保存生成版本，默认保留最近 30 个版本或 90 天 |
| SAFE-07 | P0 | 自动生成本地滚动备份 | 每日一次，至少保留最近 7 份；备份失败可见但不阻塞记录 |

### 7.3 记录生命周期

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| LIFE-01 | P0 | 查看全部记录 | 支持分页/虚拟化，不一次把全部正文和媒体载入内存 |
| LIFE-02 | P0 | 编辑记录 | 可修改正文、发生时间、分类、标签、心情和附件 |
| LIFE-03 | P0 | 收藏/取消收藏 | 操作立即本地生效并进入同步 outbox |
| LIFE-04 | P0 | 复制记录 | 生成新 ID 和新创建时间，保留正文与组织字段；附件使用引用计数或受控复制 |
| LIFE-05 | P0 | 移入回收站 | 从普通视图隐藏，保留正文、关系和附件，支持撤销 |
| LIFE-06 | P0 | 恢复记录 | 恢复到原发生日期和原组织信息 |
| LIFE-07 | P0 | 永久删除 | 二次确认，删除数据库关系；附件按引用和宽限期清理 |
| LIFE-08 | P1 | 批量管理 | 可批量添加/移除标签、改变分类、收藏和移入回收站 |
| LIFE-09 | P0 | 修改发生时间 | 创建时间保持不变，时间线按 `occurredAt` 重新排序 |

### 7.4 分类和标签

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| ORG-01 | P0 | 每条记录可选一个分类 | 未选择时为“未分类”，不强迫速记中决定 |
| ORG-02 | P0 | 每条记录可有多个标签 | 输入可搜索已有标签，也可创建新标签 |
| ORG-03 | P0 | 分类和标签持久化 | 重启、备份恢复和同步后保持一致 |

| ORG-05 | P0 | 支持删除分类/标签 | 不删除记录；记录回到未分类或移除该标签 |
| ORG-06 | P1 | 支持标签建议 | 只根据最近使用排序，不自动分析正文或上传内容 |

### 7.5 搜索和筛选

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| FIND-01 | P0 | `Ctrl+K` 在任意主窗口打开搜索 | 搜索输入自动聚焦，Esc 返回原上下文 |
| FIND-02 | P0 | 搜索标题、正文、分类和标签 | 中文连续文本、英文大小写和数字均能命中 |
| FIND-03 | P0 | 结果显示命中上下文 | 标题/正文高亮匹配片段，不只显示记录标题 |
| FIND-04 | P0 | 支持组合筛选 | 日期范围、分类、标签、心情、收藏、回收站和附件类型可组合 |
| FIND-05 | P0 | 搜索与页面语义一致 | 不支持搜索的页面不显示假搜索框；媒体搜索明确只查附件及所属记录 |
| FIND-06 | P0 | 保留最近搜索 | 只存本地，可在设置中清空，不同步为日记内容 |

实现建议：三字及以上查询使用 SQLite FTS5 `trigram` 索引；一至二字查询回退到受限 `LIKE`，并用固定的 10,000 条中文测试集验证性能。若目标 Electron 运行时不包含所需 FTS 能力，应在开发阶段直接失败并切换实现，不能在生产环境静默退化。

## 8. 关键交互规范

### 8.1 全局速记流程

```text
全局快捷键
  → 若速记窗口未显示：在当前屏幕唤起并聚焦正文
  → 若已显示且有焦点：隐藏窗口并保存草稿
  → 粘贴文字/截图/文件
  → 自动保存草稿
  → Ctrl+Enter
  → 事务保存正式记录 + 写入 outbox
  → 显示“已保存到本机”
  → 隐藏速记窗口并恢复前一应用焦点
```

- 速记窗口不能因为同步失败而保持阻塞。
- 粘贴同时包含文字和图片时两者均保留，但不解析 HTML 中的来源链接。
- 再次打开时，如果上次草稿未显式保存，优先恢复并提示“已恢复草稿”。
- “丢弃草稿”是明确操作，需可撤销或二次确认。

### 8.2 主窗口记录流程

- “今天”保留常驻编辑区，适合连续记录。
- “全部记录”采用列表 + 可选详情面板；单击选择，Enter/双击打开编辑。
- 列表项的更多菜单必须是真实按钮，包含收藏、复制、移入回收站等操作。
- 点击列表项不能是唯一入口；每项必须可聚焦并响应 Enter/Space。
- 日期按钮打开日期选择器并改变 `occurredAt`，不再作为无行为装饰。

### 8.3 删除和恢复

1. 移入回收站后展示可撤销 toast。
2. 回收站中提供恢复和永久删除。
3. 永久删除提示将删除的记录与独占附件数量。
4. 共享附件或仍被草稿引用的物理文件不得删除。
5. 同步删除使用墓碑/软删除，避免其他设备把内容重新带回。

### 8.4 搜索

- 搜索面板打开时保留原页面和选中记录；关闭后回到原上下文。
- 输入时采用 150–250 ms 防抖，先显示本地结果。
- 筛选条件以可删除的紧凑标签显示，并有“全部清除”。
- 没有结果时展示当前查询与筛选摘要，并给出可执行的调整建议。
- 打开结果后保留返回搜索结果的路径和滚动位置。

## 9. 桌面界面设计要求

### 9.1 总体方向

维持当前中性界面和克制蓝色作为基础，但让内容而不是装饰成为视觉中心。桌面端是“安静的记录工作台”，不是数据仪表盘，也不是仿纸笔记本。

- 删除 `YOUR VISUAL ARCHIVE` 等没有实际信息的英文装饰标题。
- 避免页面顶栏标题与内容区标题重复，只保留一个清晰层级。
- 主内容宽度根据任务变化：正文阅读控制在约 65–75 个字符，媒体和列表可更宽。
- 减少无功能的大面积留白，把空间用于时间线、编辑器和筛选上下文。
- 不使用嵌套卡片、装饰性渐变、玻璃效果和过度圆角。

### 9.2 字体与密度

- 使用一套可靠的无衬线字体体系，延续 Inter + 中文系统字体回退。
- 正文编辑和阅读建议 14–16 px；普通界面文字不低于 12 px。
- 8–10 px 仅允许用于非关键辅助标记，不可承载操作、同步状态或主要元数据。
- 正文行高 1.65–1.9，列表元数据保持紧凑但可读。
- 统一数字和时间的对齐方式，避免时间线视觉抖动。

### 9.3 颜色和状态

- 主强调色只用于主要操作、当前选中和焦点，不作为大面积装饰。
- 浅色和深色主题均满足正文及占位文字的 AA 对比度。
- 成功、警告、错误、同步中除颜色外还必须带图标或文字。
- 收藏、心情和附件类型不能只通过颜色区分。

### 9.4 组件状态

按钮、输入框、选择器、列表项、菜单、对话框必须定义：默认、悬停、焦点、按下、禁用、加载和错误状态。动效用于解释状态变化，时长以 150–250 ms 为主，并提供减少动态效果的替代。

### 9.5 空状态与错误状态

- 第一次打开“今天”：说明可以直接输入、粘贴截图和使用快捷键。
- 没有搜索结果：显示查询条件，提供清除筛选操作。
- 媒体损坏：显示文件名、所属记录和重新定位/移除入口。
- 同步不可用：明确“内容已保存在本机”，不使用会引发数据丢失焦虑的文案。
- 数据库不可写：立即阻止新的正式保存，保留内存草稿并给出恢复路径。

## 10. 技术架构

### 10.1 进程边界

```text
React renderer
  │ 仅调用受限的 window.diaryAPI
  ▼
preload / typed IPC boundary
  ▼
Electron main
  ├─ SQLite repository
  ├─ draft / entry / search services
  ├─ managed attachment store
  ├─ backup / restore service
  ├─ global shortcut + tray + windows
  └─ sync engine + outbox
```

- Renderer 不直接访问数据库、文件系统或 Node API。
- Main 进程负责所有持久化事务和路径校验。
- preload 只暴露按业务命名的最小 API，不暴露任意 SQL、任意路径读取或通用 IPC。
- 所有 IPC 输入在 main 端进行 schema 校验、大小限制和错误归一化。

### 10.2 模块建议

```text
desktop/src/
  main/
    windows/          # main、quick-capture、tray
    ipc/              # 按 entry/search/asset/settings 分组
    database/         # connection、migrations、repositories
    services/         # draft、backup、sync、asset lifecycle
  preload/
    index.cjs
  renderer/
    app/
    features/
      capture/
      entries/
      search/
      organization/
      media/
      review/
      settings/
    components/
    styles/
```

不要求一次性重构目录。每个阶段只迁移正在修改的模块，避免“大爆炸”重写。

### 10.3 SQLite 选型

- 数据库只能由 main 进程持有一个连接管理器。
- 默认使用 Electron 内置 Node 运行时可用的 `node:sqlite`；在 Phase 0 运行兼容性测试。
- 如果目标 Electron 版本不满足稳定性或所需 FTS 能力，使用 `better-sqlite3` 作为替代，但 repository 接口保持不变，并在 Windows 打包 CI 验证原生模块 ABI。
- 启用 WAL、foreign keys 和合理的 busy timeout。
- 每个 schema 版本通过顺序 migration 升级，禁止启动时用临时字段猜测结构。

## 11. 数据模型 v2

### 11.1 核心实体

#### `entries`

| 字段 | 说明 |
| --- | --- |
| `id` | 跨端稳定 UUID |
| `created_at` | 记录对象创建时间，不随用户改日期变化 |
| `occurred_at` | 内容发生时间，用于时间线和日历 |
| `updated_at` | 最后修改时间 |
| `deleted_at` | 进入回收站时间，空值表示正常记录 |
| `title` | 可空标题 |
| `content` | 原始编辑内容 |
| `content_text` | 搜索和预览用纯文本 |
| `editor_type` | `plain_text` / `markdown` / `rich_text` |
| `category_id` | 可空外键，空值显示为“未分类” |
| `mood` | 可空，只有主动选择才参与统计 |
| `is_favorite` | 收藏状态 |
| `is_pinned` | P1 预留，P0 可不在界面暴露 |
| `revision` | 本地单调版本号，用于版本和同步判断 |

#### 其他表

- `categories(id, name, sort_order, created_at, updated_at)`
- `tags(id, name, normalized_name, created_at, updated_at)`
- `entry_tags(entry_id, tag_id)`
- `attachments(id, sha256, kind, mime_type, byte_size, original_name, relative_path, created_at, state)`
- `entry_attachments(entry_id, attachment_id, sort_order, caption)`
- `drafts(id, target_entry_id, payload_json, updated_at)`
- `entry_versions(id, entry_id, revision, snapshot_json, created_at)`，P1 启用
- `outbox(mutation_id, entity_type, entity_id, payload_json, created_at, retry_count, next_retry_at)`
- `sync_state(key, value)`
- `settings(key, value_json, updated_at)`
- `migration_log(version, applied_at, checksum)`

### 11.2 v1 兼容规则

- `createdAt` 暂时映射到 v2 的 `occurredAt`；迁移时新的 `createdAt` 使用旧 `createdAt`，保证历史排序不变。
- v1 的 `isInTrash` 映射为 `deletedAt`：为真时使用 `updatedAt` 作为近似删除时间。
- v1 的 `category` 字符串去重后写入 `categories`。
- v1 的 `tags` 去重、规范化后写入多对多关系。
- v1 的 `imagePaths`、`audioPaths`、`videoPaths` 转换为附件实体和关系。
- 为兼容协议 v1，未填写心情时可发送 `mood: 0.5` 和扩展字段 `moodSet: false`；协议 v2 改为真正可空。
- 新模型不得把自动生成的列表摘要写回 `title`。

## 12. 从 localStorage 迁移到 SQLite

### 12.1 迁移流程

1. 启动时检测 SQLite `migration_log` 和 localStorage v1 数据。
2. 把 v1 JSON 原样写入带时间戳的恢复文件，不立刻删除 localStorage。
3. 在单个数据库事务中迁移记录、分类、标签、附件引用、outbox、cursor、设备 ID 和设置。
4. 校验迁移前后记录数、回收站数、附件引用数和 mutation 数。
5. 写入迁移报告和完成标记，再让 renderer 读取 SQLite 数据。
6. 至少跨一个稳定版本保留只读恢复文件；明确提供“从迁移备份恢复”。
7. 迁移失败时回滚数据库事务，继续使用只读故障页，不覆盖原始数据。

### 12.2 附件迁移

- 已位于 Electron `userData/media` 的文件不重复复制，只计算哈希并改为相对路径。
- 外部绝对路径先验证是否可读，再复制到按哈希分层的受管目录。
- 丢失文件建立 `missing` 状态的附件记录，保留原文件名和关联记录，供用户重新定位。
- 任何失败项进入迁移报告，不能静默删除附件引用。

## 13. 同步协议演进

### 13.1 当前阶段

- 保留本地优先和 outbox，不让保存等待服务端。
- 修复当前“冲突后直接采用服务端版本”的行为：服务端版本进入当前记录，本地失败版本进入冲突箱。
- 同步状态按实体级 mutation 确认，失败继续指数退避。
- 设备时间明显异常时提示用户，减少 LWW 对系统时钟的依赖风险。

### 13.2 协议 v2

- 记录正文、分类、标签、附件元数据成为独立但可批量同步的实体。
- 删除使用 tombstone，并定义保留时间与设备确认策略。
- 附件上传与文本同步分离，正文先同步，媒体在后台补传。
- 附件以 SHA-256 校验完整性；下载到临时文件后校验成功再原子替换。
- `occurredAt`、`deletedAt`、可空 `mood` 和版本信息进入正式 schema。
- 在实现 APP 同步客户端前，先用两台桌面测试设备验证断网、重试、并发编辑和删除恢复。

## 14. 安全和隐私边界

- Electron 保持 `contextIsolation: true`、`nodeIntegration: false`。
- 任意文件读取 IPC 必须限制到附件根目录或由系统文件选择器返回的授权路径。
- 导入文件名必须去除路径穿越和 Windows 非法字符。
- Web 内容按纯文本粘贴；未来若支持富文本，必须经过白名单净化，不能执行 HTML。
- 同步 token 不存入 renderer localStorage；使用系统凭据存储或 main 进程安全配置。
- 日志不得记录日记正文、搜索词、token 或附件内容。
- “应用锁”只防止临时查看，不得宣传为磁盘加密。
- 加密功能上线前必须补充威胁模型、密钥恢复、备份加密和多设备换机方案。

## 15. 测试策略

### 15.1 测试层次

- 单元测试：字段规范化、摘要生成、筛选组合、快捷键解析、附件路径校验。
- 数据库集成测试：migration、事务回滚、草稿、标签合并、删除恢复、附件引用清理、FTS 索引。
- Renderer 组件测试：键盘导航、焦点恢复、空状态、错误状态、菜单和对话框。
- Electron 端到端测试：全局速记、主/速记窗口通信、粘贴附件、保存、重启恢复、托盘退出。
- 同步契约测试：幂等重试、分页游标、冲突箱、tombstone 和附件元数据。
- 备份往返测试：导出后在空资料库导入，记录、关系、附件哈希完全一致。

### 15.2 建议工具

- `Vitest`：React 逻辑、services 和 repository 单元/集成测试。
- `React Testing Library`：交互与可访问性测试。
- `Playwright` Electron：关键桌面流程。
- 现有 server 测试继续作为同步契约回归入口。

### 15.3 必测故障

- 写入数据库时磁盘空间不足或权限被撤销。
- 草稿保存途中强制结束进程。
- 附件复制一半失败、源文件消失或哈希不一致。
- 导入损坏 ZIP、旧 schema、重复 ID 和缺失附件。
- 同步超时、重复响应、乱序变更、两设备同时编辑和删除。
- 全局快捷键被其他应用占用。
- 多屏切换后速记窗口坐标落在不可见区域。

## 17. 首批开发任务拆分

当前第一批 Phase 0–1 已完成，Phase 2 速记主链路已开始接入。后续继续按小切片推进，避免一次性重写界面：

1. `desktop-db-spike`：验证 SQLite、FTS、WAL、打包和 Windows CI。
2. `desktop-repository`：实现 entry/draft/outbox/settings repository 与事务。
3. `desktop-v1-migration`：实现 localStorage 备份、迁移、对账和恢复报告。
4. `desktop-preload-api`：定义受限 IPC、schema 校验和错误类型。
5. `desktop-draft-autosave`：接入编辑器自动保存和崩溃恢复。
6. `desktop-data-safety-tests`：覆盖强制退出、迁移失败、磁盘错误和附件丢失。
7. `desktop-quick-capture`：补充快捷键设置、冲突提示、多屏定位和 Electron 端到端流程。

速记窗口已复用 SQLite 和事务草稿；后续补齐真实缩放/多屏 E2E、错误恢复和完整桌面端到端验收。

## 18. 发布门槛

每个阶段必须同时满足以下条件才能进入下一阶段：

- 不会把正文、附件或 token 写入日志。
- 鼠标与键盘核心流程均通过验收。

## 19. 主要风险与应对

| 风险 | 应对 |
| --- | --- |
| localStorage 迁移导致历史数据丢失 | 原始 JSON 只读备份、事务迁移、数量/引用对账、至少保留一个稳定版本 |
| Electron SQLite/原生模块打包差异 | Phase 0 先做 Windows 打包验证，repository 隔离具体驱动 |
| 全局快捷键与其他应用冲突 | 注册结果可见、允许修改、提供托盘入口作为替代 |
| 附件占用磁盘快速增长 | 哈希去重、缩略图、使用量展示、回收站宽限和可解释清理 |
| LWW 覆盖有价值的修改 | 冲突箱保留失败版本，协议 v2 再演进更细的冲突策略 |
| 功能持续膨胀成知识库/任务工具 | 以 PRODUCT.md 的反例和本方案“暂不实施”作为评审门槛 |
| 先做桌面后忽略手机 | 数据模型与验收语义跨端定义；Phase 7 明确移动端对齐且不复制桌面 UI |

## 20. 竞品调研带来的取舍

- Diarium 证明多附件、标签、心情、时间线、日历、搜索、回顾、导出和应用锁可以组成完整的个人日记闭环；本产品吸收能力范围，但保持更轻的记录入口。[Diarium 官方功能](https://diariumapp.com/en)
- Journey 展示了跨平台时间线、搜索/筛选、模板、备份和回顾的成熟组合；本产品不复制地图等非核心上下文。[Journey 官方介绍](https://support.journey.cloud/en/categories/journey-basics/articles/what-is-journey)
- Daylio 的低摩擦情绪/活动记录说明“少输入也能完成一条记录”很重要；本产品保留自由文本为核心，不变成纯量化打卡。[Daylio 官方网站](https://daylio.net/)
- Day One 的 Mac 快速记录、键盘入口、模板、版本历史和导出能力说明桌面体验需要系统级入口与数据可迁移性；Windows 端的全局速记可以成为本产品的重要体验优势。[Day One 键盘快捷键](https://dayoneapp.com/guides/tips-and-tutorials/keyboard-shortcuts/)、[Day One 模板](https://dayoneapp.com/guides/tips-and-tutorials/templates/)、[Day One 版本历史](https://dayoneapp.com/guides/troubleshooting/entry-version-history/)

竞品功能只用于校验能力是否完整，不作为逐项照搬清单。任何新功能仍需回答：它是否让记录更快、更安全、更容易找回或更值得回顾。
