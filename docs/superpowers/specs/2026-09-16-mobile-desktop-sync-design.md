# APP 与桌面端一致性设计：同步、冲突与附件工作流

> 日期：2026-09-16  
> 状态：实施中（核心链路已落地）
> 范围：Flutter APP、Electron 桌面端、Node.js 同步服务

## 1. 已确认的产品决策

1. APP 与桌面端共用同一个同步资料库。
2. 两端都支持离线新增和编辑，前台约 30–60 秒同步一次；启动和回到前台立即同步。
3. 两端每天可能产生大量新记录，不能用覆盖式导入或全量替换保证一致性。
4. 同一条记录发生离线冲突时保留双方内容，生成稳定 ID 的冲突副本。
5. 冲突副本进入独立冲突中心，默认不出现在普通时间线和普通搜索中。
6. APP、桌面端和服务器不采用端到端加密；服务器可以读取明文。
7. 生产环境仍必须使用 HTTPS、Bearer Token、目录权限和受保护的备份。
8. APP 保留 Flutter + Isar，桌面端保留 Electron main + SQLite；只共享协议、字段语义和测试样例。

## 2. 目标与非目标

### 2.1 目标

- 手机和桌面端最终看到相同的主记录、冲突副本和附件状态。
- 本地写入不等待网络，断网时仍可连续记录。
- 网络恢复后，outbox、记录变更和附件队列可重试并最终收敛。
- 不因重复请求、重复导入、应用崩溃或分页拉取造成重复记录或数据丢失。
- APP 具备桌面端已验证的速记、全部记录、组合筛选、媒体回链、回收站和备份恢复能力。

### 2.2 非目标

- 不在本阶段引入端到端加密、多人协作或公共分享。
- 不要求移动系统后台持续运行；后台同步只能尽力执行。
- 不把 APP 改造成桌面端的缩小版，底部导航和单手交互保持独立。
- 不把标签扩展为任务、项目或多层文件夹系统。

## 3. 总体架构

```text
Flutter APP (Isar)       Electron Desktop (SQLite)
        │                         │
        ├── local entry/assets    ┤
        ├── outbox + sync cursor  ┤
        └────── Sync Engine ─────┘
                    │ HTTPS + Token
          Node Sync API v2 + change log
                    │
          data/store.json + data/assets/
```

服务端先继续使用当前 JSON 文件存储，附件放入 `data/assets/<sha256>`。存储接口与 HTTP 协议保持解耦，后续可以替换为 SQLite、PostgreSQL 或对象存储，不改变客户端同步语义。

## 4. 本地数据模型

### 4.1 Entry

在现有字段基础上统一补齐：

- `occurredAt`：用户记录实际发生时间；
- `revision`：客户端本地版本号；
- `deletedAt`：软删除时间；
- `deviceId`：最后修改设备；
- `isConflict`、`conflictOf`、`conflictStatus`：冲突副本标识和处理状态；
- `attachmentIds`：稳定附件 ID 列表。

现有 `imagePaths`、`audioPaths`、`videoPaths` 保留为兼容字段，界面和新同步逻辑优先使用附件实体。

### 4.2 Attachment

两端都维护独立附件实体：

```text
assetId          稳定 ID，默认使用 asset-<sha256>
sha256           文件完整性与去重依据
kind             image / video / audio / file
mimeType         MIME 类型
byteSize         字节数，单文件上限 128 MB
originalName     原始文件名
localPath        本机受管目录路径，可为空
remoteState      local_only / uploading / uploaded / downloading / ready / missing / failed
lastError        最近一次上传或下载错误
createdAt        创建时间
```

APP 使用应用目录保存本地附件，桌面端使用现有 `media/managed`。两端都禁止把外部绝对路径当作长期同步标识。

### 4.3 Outbox、SyncState、Conflict

- `Outbox`：`mutationId`、`entityType`、`entityId`、`payload`、`retryCount`、`nextRetryAt`、`createdAt`。
- `SyncState`：`deviceId`、`cursor`、`lastSuccessAt`、`lastError`、`serverUrl`。
- `Conflict`：`conflictId`、`entryId`、冲突版本快照、来源设备、来源 mutation、创建时间、`pending/resolved` 状态。

APP 在 Isar 中新增 collection；桌面端使用现有 SQLite 表和迁移机制。两端的 repository 都提供相同语义的方法，但不共享实现代码。

## 5. 协议 v2 与同步流程

### 5.1 接口

- `POST /api/v2/sync`：推送本地 mutations，同时按 cursor 拉取变更。
- `PUT /api/v2/assets/:sha256`：上传一个附件，按 SHA 幂等。
- `HEAD /api/v2/assets/:sha256`：检查附件是否已存在。
- `GET /api/v2/assets/:sha256`：鉴权后流式下载附件。

现有 `/api/v1/sync` 保留兼容适配。APP 和桌面升级后使用 v2；v1 客户端仍可读写主记录，但不会参与冲突中心和附件队列。

### 5.2 单次同步

1. 从本地事务读取尚未确认的 outbox，最多 100 条。
2. 将记录 mutation 和附件元数据一起推送；不把二进制塞入 JSON。
3. 服务端按 `updatedAt + deviceId + mutationId` 确定版本顺序，并用 `mutationId` 保证幂等。
4. 服务端返回已接受 mutation、冲突事件和 cursor 范围内的远端变更。
5. 客户端开启本地事务：应用远端主记录、写入冲突副本、确认 outbox。
6. 只有本地事务提交成功后才推进 cursor；失败则保留原 cursor 和 outbox，下一次重试。
7. 若返回页已满或 cursor 尚未追平，继续拉取，直到本地追平服务器。
8. 文本同步完成后处理附件上传/下载队列；附件失败不回滚正文。

### 5.3 重试与状态

- 网络错误、超时和服务端 5xx 保留 outbox，指数退避 1、2、4、8 分钟，最长 15 分钟。
- 4xx 数据校验错误不无限重试，显示具体记录和修复入口。
- 前台定时器按 30–60 秒执行；启动、回到前台、手动刷新立即执行一次。
- 移动端后台任务只作为加速手段，不能作为一致性前提。

## 6. 冲突副本与冲突中心

### 6.1 服务端冲突记录

当服务端拒绝一个较旧 mutation 时，不丢弃它，而是创建：

```text
conflictId = conflict:<entryId>:<mutationId>
entry.id   = conflictId
isConflict = true
conflictOf  = entryId
```

冲突副本作为独立变更事件写入 change log，并在其他设备拉取时返回。主记录仍保持服务端当前版本。重复收到同一 mutation 或冲突事件不会产生第二份副本。

### 6.2 APP/桌面端交互

- “我的”中显示冲突中心入口和未处理数量徽标。
- 冲突详情显示主记录、冲突副本、来源设备和时间。
- 可选“保留主记录”“保留冲突副本”“手动合并”。
- 纯文本支持编辑合并结果；富文本无法安全自动合并时提供版本选择。
- 解决动作生成新的 resolution mutation，服务端确认后两端同时标记 `resolved`。
- 冲突副本默认不计入普通记录数、不出现在普通时间线和普通搜索；冲突中心可单独搜索。

## 7. 附件生命周期

### 7.1 上传

客户端先计算 SHA-256，将附件元数据和记录一起写入本地。同步引擎先用 `HEAD` 检查远端；缺少时使用 `PUT` 上传原始字节。服务器校验大小、MIME 和 SHA 后写入临时文件，再原子改名为 `<sha256>`。

### 7.2 下载

远端记录到达后，如果本地没有对应 SHA，建立 `downloading` 队列。下载到临时文件，校验 SHA 成功后原子移动到本地受管目录，再把状态改为 `ready`。文件不存在、校验失败或权限错误均保留为 `missing/failed`，提供重试。

### 7.3 去重与清理

- 同一 SHA 只保留一份物理文件，多条记录通过关系引用。
- 回收站记录仍持有附件引用，不能提前删除。
- 无记录、无草稿引用的附件经过宽限期后才清理。
- 桌面端已有 staging 和孤儿清理逻辑，APP 采用同样的临时目录与宽限期原则。

## 8. APP 页面与交互映射

### 8.1 一级入口

保留底部五项：今天、日历、媒体、洞察、我的。快速记录使用全局悬浮按钮。

### 8.2 今天与编辑器

- 快速记录保存后立即进入本地时间线，并显示本地保存状态。
- 分类、标签、心情全部平铺；标签按使用频率排序，频率相同时按最近使用排序。
- 编辑器支持纯文本、Markdown、富文本、图片/视频/音频/文件和自动草稿。
- 标签可一键切换和新建，不使用必须打开两次的下拉菜单。

### 8.3 全部记录与搜索

- 从今天和我的进入全部记录。
- 搜索支持标题、正文、分类、标签。
- 筛选支持日期范围、分类、多个标签、心情、收藏、附件类型和回收站。
- 搜索结果显示命中上下文，分页加载，不一次性拉取全部记录。

### 8.4 媒体、回收站和我的

- 媒体页支持按类型、关键词和所属记录筛选，缺失附件显示原因与重试。
- 回收站支持恢复和永久删除；永久删除前显示记录和独占附件影响。
- 我的包含冲突中心、分类/标签管理、备份恢复、同步状态和设置。

### 8.5 桌面端基线功能矩阵

APP 不复制桌面端布局，但必须对齐桌面端已经验证的业务能力、字段语义和操作结果。以下矩阵是 APP 的 P0 验收基线：

| 能力 | 桌面端基线 | APP 目标 | 优先级 |
| --- | --- | --- | --- |
| 速记/编辑 | 文本速记、粘贴/拖入媒体、标题、心情、分类、标签、草稿自动保存 | 一键速记、系统分享/图片/文件入口；同样的元数据；自动保存与恢复 | P0 |
| 全部记录 | 独立列表、分页、关键字/日期/分类/标签/心情/收藏/附件筛选 | 独立“全部记录”入口，完整筛选、分页/虚拟列表 | P0 |
| 批量管理 | 批量收藏、移入回收站、整理分类/标签，移入回收站可撤销 | 多选工具栏、批量操作、撤销提示 | P0 |
| 分类/标签 | 平铺单击选择；按使用频率与最近使用排序；可重命名、删除、合并 | 分类和标签统一持久化；所有入口使用平铺 chips；排序和管理语义一致 | P0 |
| 媒体库 | 按类型/关键字筛选，回看所属记录，附件哈希、健康状态、迁移/重试 | 独立附件实体、缩略图缓存、上传/下载队列、缺失/失败/重试/迁移状态 | P0 |
| 回收站 | 恢复、永久删除、批量处理，关联附件影响可见 | 批量恢复/永久删除、撤销和附件影响提示 | P0 |
| 备份恢复 | `.diary.zip`、预览、按 ID 合并、附件打包、暂存校验、失败回滚 | 同一 ZIP 格式、导入预览、合并/跳过/覆盖策略、暂存与回滚 | P0 |
| 同步 | 当前已有 v1 推送/拉取；最终升级为 v2 | 共用 v2 协议、outbox/cursor、重试和冲突中心 | P0 |
| 日历/洞察 | 统计和日期可回到统一记录筛选 | 点击统计或日期进入同一筛选结果，不维护第二套查询逻辑 | P1 |
| 状态与设置 | 数据库、附件、备份状态和错误可追踪 | 同步地址/token、最近同步、待处理数量、冲突入口和可恢复错误 | P0 |

当前 APP 的主页搜索、单条删除、分类选择和媒体类型筛选只能视为已有基础，不满足上表的 P0 验收。尤其是分类/标签的页面内状态、JSON 覆盖式导入、单条回收站操作和缺少 outbox，必须在进入最终验收前消除。

桌面端 v1 同步是迁移期间的兼容实现，不是跨设备的最终标准。服务端、桌面端和 APP 都切换到 v2 后，才以同一组跨端 fixtures 验证记录、冲突和附件收敛；在此之前不将 APP 的局部功能标记为“已对齐”。

### 8.6 移动端适配边界

- 底部导航、悬浮速记按钮、手势返回和系统分享入口保留移动端习惯。
- “全部记录”必须一级可达，可从今天页和我的页进入；不能只隐藏在主页搜索框中。
- 洞察和日历可以保持独立页面，但点击结果必须复用全部记录的筛选状态。
- 分类、标签、批量操作、媒体队列和同步状态不因屏幕尺寸而降级为下拉菜单或不可见的后台行为。

## 9. 迁移策略

1. 打开现有 Isar/SharedPreferences 数据并创建本地恢复副本。
2. 为旧记录补齐 `occurredAt`、`revision = 1`、`deviceId` 和软删除字段。
3. 将旧媒体路径登记为附件实体：文件存在则计算 SHA 并复制到受管目录，文件缺失则保留原文件名并标记 `missing`。
4. 为迁移产生的本地记录生成初始 outbox；迁移不重复生成已有稳定 ID。
5. 对账记录数、回收站数、附件数、附件引用数和 outbox 数。
6. 对账通过后写迁移版本标记；失败时恢复副本并保留错误报告。

## 10. 备份与恢复

APP 和桌面统一使用 `.diary.zip`，包含：

```text
manifest.json
entries.json
attachments.json
settings.json
attachments/*
```

导入先校验 ZIP 路径、大小、JSON 结构和附件 SHA，再显示记录数、附件数、时间范围和预计冲突数。默认按稳定 ID 合并，不覆盖本地较新记录；附件先进入 staging，数据库事务失败时只清理本次新文件。重复导入按记录 ID 和附件 SHA 去重。

## 11. 安全与错误处理

- 服务器明文存储是已确认的产品决策；部署必须使用 HTTPS 和 Bearer Token。
- 服务端附件目录和备份文件限制系统权限，不在日志中记录正文、搜索词、Token 或附件内容。
- UI 明确区分“已保存到本机”“待同步”“同步失败”“有冲突”“附件待上传/待下载”。
- 同步错误提供重试；冲突提供处理入口；附件错误提供重新上传、重新下载或重新定位。
- 文件读取、上传、下载都限制在受管目录或明确的文件选择器路径内。

## 12. 测试与验收

### 12.1 单元与集成测试

- APP：Isar schema/migration、repository 事务、outbox 合并、cursor 推进、冲突副本、附件哈希和队列重试。
- 桌面端：现有 SQLite/备份测试扩展到 v2 change、冲突副本和附件同步。
- 服务端：认证、幂等 mutation、分页 cursor、冲突事件、附件 HEAD/PUT/GET、SHA/大小校验和原子写入。
- 跨端固定 fixture：同一批记录在 APP、桌面端导入后字段、主键、附件 SHA 完全一致。

### 12.2 验收标准

- 两端各离线新增 1,000 条记录，恢复网络后最终记录集合和字段完全一致。
- 同一条记录制造双端离线编辑，主记录和冲突副本在两端都出现，且只生成一份冲突副本。
- 断网、超时、重复请求、客户端重启不会丢失 outbox 或重复记录。
- 附件上传中断后可重试；下载后 SHA 一致；服务器缺失时客户端状态可解释。
- 备份在空资料库和已有资料库导入后，正文、组织关系和附件 SHA 一致。
- 前台恢复网络后 60 秒内完成一次同步循环；同步失败时本地写入仍可继续。

## 13. 实施顺序

1. **M0 数据模型与迁移**：APP Isar 新 collection、桌面 SQLite 字段、版本化迁移和恢复副本。
2. **M1 协议 v2 与同步引擎**：服务端 change log、outbox/cursor、幂等重试，先同步纯文本和组织字段。
3. **M2 冲突中心**：服务端冲突事件、两端冲突副本、查看和解决 mutation。
4. **M3 附件同步**：服务器资产接口、两端上传/下载队列、媒体状态和缺失恢复。
5. **M4 APP 交互对齐**：全部记录、组合筛选、平铺 taxonomy、媒体回链、回收站和同步状态。
6. **M5 APP 备份与验收**：`.diary.zip` 往返、迁移对账、跨端 fixture 和真实设备 E2E。

本设计不把任何一端当作主产品；APP 和桌面端最终共享同一套记录、冲突和附件语义，只在交互形式上保持平台差异。
